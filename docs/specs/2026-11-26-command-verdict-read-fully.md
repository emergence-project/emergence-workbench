# 설계: 끝까지 읽은 명령만 묻지 않고 지나가기

2026-11-26 · 상태: 사용자 승인 (11/26, 10절 모두 제안대로), 구현 · 범위: 에이전트 대화의 Bash 명령 판정

## 1. 왜 하는가

에이전트 대화의 Bash 명령은 앱이 하는 일로 나눠(읽기 · 편집 · 삭제 · 실행 · 외부) 묻거나 지나가게 한다. 지금은 **알아본 위험한 꼴만 묻고 나머지는 지나간다.** 모르는 프로그램, 변수로 정한 프로그램, 풀지 못한 치환은 모두 「실행」이 되고, 「자동」과 실행 「늘」에서는 묻지 않는다.

그래서 판정이 놓친 꼴이 나올 때마다 그 꼴을 막는 PR을 올렸다. 11/20부터 11번이고(#613 · #614 · #618 · #619 · #681 · #688 · #690 · #691 등), 그중 세 번은 고치다가 더 가벼운 판정을 만들었다. 막을 꼴의 끝이 없으므로 이 일에는 끝나는 조건이 없다.

이 설계는 방향을 뒤집는다. **끝까지 읽은 줄만 지나가고, 읽지 못한 줄은 묻는다.** 그러면 새 꼴이 나와도 묻게 되므로 꼴을 하나씩 막을 일이 없다.

### 판정이 걸리는 길 (지금)

이 판정이 모든 대화에 걸리는 것은 아니다. `agentPolicy.ts`가 대화와 권한에 따라 길을 가른다.

| 대화 | 권한 | Bash 명령 |
| --- | --- | --- |
| 연구 프로젝트 | 묻고 하기 · 편집 자동 허용 | 하는 일로 판정 (`judgeCommand`) |
| 연구 프로젝트 · 앱 고치기 | 자동 | 하는 일로 판정 (`judgeAuto`) |
| 앱 고치기 | 묻고 하기 | 판정 없이 명령마다 그대로 묻는다 |
| 앱 고치기 | 편집 자동 허용 · 승인된 계획 | **판정 없이 모두 허락한다** (올리기 · PR · 합치기 · 앱 서비스만 거절) |
| 중앙 | | 허락 목록 (`stateOnlyCommand`) |

이 맥에 남은 대화 36개 가운데 앱 고치기 34개가 모두 「편집 자동 허용」이었고, 거기서 허락을 물은 기록은 없다. 곧 명령의 대부분(1,858개 가운데 1,719개)은 지금 판정을 거치지 않는다. 이 설계가 바꾸는 것은 위 표의 첫 두 줄이고, 넷째 줄을 어떻게 할지는 10절에서 사용자가 정한다.

## 2. 목표와 목표가 아닌 것

**목표**

1. Bash 명령이 묻지 않고 지나가려면 (가) 지금 판정이 허락하고 (나) 줄이 끝까지 읽혀야 한다.
2. 새 검사는 허락을 묻기로만 바꾼다. 지금 묻거나 거절하는 줄의 판정은 그대로다.
3. 실제 대화에서 새로 묻는 줄은 1% 안팎이다(4절의 측정).
4. 끝나는 조건을 테스트로 적는다(7절).

**목표가 아닌 것**

- 인라인 코드(`python3 -c` · `node -e` · 히어독으로 준 코드) 안을 읽는 것. 지금처럼 지나간다. 판정은 그 안을 읽지 못하고, 작업 폴더 안의 편집과 실행을 허락하는 한 에이전트는 스크립트 파일을 쓰고 돌릴 수 있어 물어도 닫히지 않는다. 이 한계는 소개에 적는다.
- 작업 폴더 밖을 못 쓰게 막는 벽. 그것은 OS 격리의 일이고 8절의 시험 결과를 보고 따로 설계한다.
- 중앙 대화. 이미 허락 목록 방식(`stateOnlyCommand`)이라 그대로 둔다.
- 삭제 · 외부 · 비밀 · 크리티컬 판정과 읽기 전용 · 계획 승인 전 거절. 그대로 둔다.

**하면 안 되는 것**

- 어떤 줄이든 지금보다 가볍게 판정하는 것.
- 기존 읽기 코드(`chat-auto.ts` · `chat-shell.ts`)의 판정을 바꾸는 것. 목록 내보내기처럼 뜻이 그대로인 변경만 한다.
- 대화마다 묻는 횟수가 눈에 띄게 느는 것(7절의 한도 5%).

## 3. 제약

- 이 영역은 최근 회귀가 세 번 나온 곳이다. 새 읽기 규칙은 원래 판정을 대신하지 않고 더한다.
- 판정 PR은 CI와 별도로 (1) 결론을 모르는 검토와 (2) main과 나란히 돌린 비교를 거친 뒤 합친다.
- `apps/server/src/agentPolicy.ts`는 이식 안내서 `docs/ports/agent-chat.md`의 `code:` 파일이다. 안내서와 소개 절(`apps/web/src/about/agents/agent-conversations.tsx`, ko · en)을 같은 PR에서 고치고 `apps/web/src/about/prs/<PR 번호>.json`에 적는다.
- 구조 래칫: 새 파일은 600줄을 넘지 않고, 기준에 닿아 있는 파일의 줄 수를 늘리지 않는다.
- 열린 PR은 한 번에 하나다. 지금 #674 · #671이 열려 있으니 시작 전에 사용자에게 알린다.

## 4. 측정

이 맥에 남은 앱 고치기 대화 34개의 Bash 명령 2,104줄(중복 제외)을 「자동」의 판정에 넣어 보고, 새 검사도 임시로 돌렸다(#691이 합쳐진 main 기준). 이 줄들은 실제로는 판정 없이 지나갔다(1절). 아래는 "같은 명령이 「자동」에서 돌았다면"의 숫자다.

| | 줄 수 | 비율 |
| --- | --- | --- |
| 「자동」의 지금 판정이 묻는 줄 (삭제 · 외부) | 76 | 3.6% |
| 「자동」의 지금 판정이 지나가게 하는 줄 | 2,028 | |
| 그중 인라인 코드 (지나감, 이 설계 밖) | 384 | 19% |
| 그중 새 검사가 묻게 될 줄 | 약 17 ~ 25 | 1% 안팎 |

새로 묻는 줄의 까닭: 셸 내장 `set` · `setopt` 13, 옵션 자리의 변수 9, 환경 변수를 앞에 붙인 실행 9, 모르는 프로그램 9(perl 5, 그 밖 4), 쓰기 대상의 변수 8, 변수로 정한 프로그램 2. 한 줄에 까닭이 여럿일 수 있고, `set -e`와 글자 값 환경 변수는 5절에서 허용하므로 실제는 이보다 적다.

**한계.** 임시 검사는 5.2의 규칙과 같은 뜻으로 짰지만 같은 코드는 아니다. 앱 고치기 대화만 셌다. 연구 프로젝트 대화는 남은 명령이 136줄뿐이라 근거가 약하다(거기서 쓰인 실행 프로그램은 `python3` · `curl` · `gh` · `git` · `lsof` · `ps` · `hostname`). 아는 프로그램 목록은 이 기록에서 골랐으므로 다른 일에서는 더 물을 수 있다.

## 5. 설계

### 5.1 규칙

`agentPolicy.ts`에서 Bash 명령에 허락(`allow`)을 돌려주는 모든 자리 앞에 검사 하나를 둔다.

```
지금 판정이 허락함  →  줄이 끝까지 읽혔나?
                         예      →  허락 (지금과 같음)
                         아니오  →  한 번 묻기
```

거는 자리: 「자동」(`judgeAuto`)의 읽기 · 편집 · 실행 허락과 `pnpm install --frozen-lockfile` 허락, 연구 프로젝트 대화의 「묻고 하기」 · 「편집 자동 허용」(`judgeCommand`)의 읽기 토글 · 편집 허락 · 실행 토글과 실행 「늘」 허락. 자리마다 따로 넣지 않고 허락을 돌려주는 길을 도우미 하나로 모은다.

걸지 않는 자리: 앱 고치기 대화의 「편집 자동 허용」(`judgeApp`이 판정 없이 허락하는 줄). 거기에 이 검사만 걸면 `rm -rf`는 지나가고 `setopt`는 묻게 되어 앞뒤가 맞지 않는다. 그 길은 10절의 결정에 따른다.

### 5.2 "끝까지 읽혔다"의 뜻

새 파일 `packages/core/src/chat-known.ts`의 함수 하나가 정한다. 줄을 읽지 못했으면 까닭을 돌려주고, 다 읽었으면 없음을 돌려준다. 셸 글 읽기는 `chat-shell.ts`의 함수를 그대로 쓴다.

지금 읽기는 모르는 것을 만나면 「실행」으로 접는다. 이 검사는 그 "모름"을 따로 꺼내 묻게 한다. 읽지 못한 것은 세 묶음이다.

**가. 프로그램 자리 (허락 목록).** 명령마다(치환과 감싸 돌리기 안의 명령도) 앞말(`time` · `nice` · `nohup` · `command` · `timeout` · `env` 등 `leading()`이 떼는 것)과 대입을 뗀 첫 낱말이 5.3의 아는 프로그램이어야 한다. 변수 · 치환 · 무늬 · 중괄호로 만든 이름과 목록에 없는 이름은 읽지 못한 것이다.

**나. 지금 읽기가 스스로 모른다고 한 자리.** `chat-auto.ts`가 확신 없이 「실행」으로 올리는 자리는 모두 읽지 못한 것이다.

- 풀지 못한 치환 (`substitutions`의 `left`)
- 변수 값을 다 넣어 보지 못함 (`variants`의 `partial`, 횟수 한도)
- 다른 프로그램을 돌리게 할 수 있는 환경 변수를 앞에 붙임 (`leading`의 `env`)
- 무늬 한정자가 코드를 돌림 (`qualifierRuns`), zsh의 다시 펼치기 `${(e)…}` (`evalFlags`)
- 감싸 돌리기가 깊이 한도를 넘음

**다. 더 묻는 꼴.**

| 꼴 | 까닭 |
| --- | --- |
| `eval` · `source` · `.` · `exec` · `trap` · `alias` · `builtin` · `noglob` · `repeat` · `coproc` · `select` · `case` · `setopt` · `unsetopt`, 함수 정의 | 뒤의 글이 명령으로 다시 읽히거나, 읽기가 다루지 않는 문법 |
| `set`에 `-e` `-u` `-x` `-o pipefail` 밖의 인자 | 셸 동작을 바꿈 |
| zsh 펼침 플래그 `${(…)…}`, `=( )` | 값이 명령 · 옵션으로 펼쳐질 수 있음 |
| 옵션을 가리는 프로그램(`find` `git` `sed` `sort` `xargs` `awk` `rg` `tar` `rsync` 등)의 인자에 값을 모르는 변수 | 변수가 옵션이 될 수 있음 |
| 쓰기 대상(돌려보내기, `mv` `cp` `tee` 등의 인자)에 값을 모르는 변수나 치환 | 폴더 밖을 쓸 수 있음 |

값을 아는 변수는 같은 줄에서 글자 값으로 정해진 것(대입 · `for` 낱말, 지금의 `noteVars`)과 `$HOME` · `$PWD` · `$TMPDIR`다.

**읽은 것으로 치는 것 (지금처럼).** 위 세 묶음에 걸리지 않으면 읽은 것이다. 따옴표, `;` `&&` `||` `|`, 돌려보내기, `for` · `while` · `until` · `if`, `[[ ]]`, `(( ))`, `{ }`, `( )`, 인자의 무늬 · 중괄호 · `${x:-값}` · `$1` · `$?`, 값을 모르는 대입(`x=$(…)`), 셸 내장 `exit` · `break` · `continue` · `return` · `shift` · `:` · `wait` · `local` · `export` · `unset`, 자료를 주는 히어독, 인라인 코드(2절의 한계)가 여기에 든다. 이 문법 안에서 잘못 읽는 것은 지금처럼 읽기의 버그이고, 이 설계가 없애지 않는다(7절의 표).

### 5.3 아는 프로그램

1. 판정이 이름으로 다루는 것 전부: `chat-auto.ts`의 읽기 · 편집 · 삭제 · 외부 목록, `git`, `xargs`, 셸(`sh` · `bash` · `zsh`), 꾸러미 관리자(`npm` · `pnpm` · `yarn` · `pip` · `cargo` 등 `kindOf`가 하위 명령을 보는 것), 5.2에서 읽은 것으로 친 셸 내장.
2. 개발 도구 목록(아래, 사용자가 정한다).
3. 사용자가 실행 「늘」로 허락한 프로그램(지금의 열쇠 `run:<프로그램>`).
4. 작업 폴더 안의 스크립트 파일을 직접 돌리는 것(`./scripts/x.sh`). 에이전트가 쓸 수 있는 파일이라 인라인 코드와 같다.

경로로 적은 프로그램은 마지막 이름으로 본다(`/opt/homebrew/bin/python3`는 `python3`).

**개발 도구 목록 (제안):** `pnpm` `npm` `npx` `node` `tsx` `tsc` `vitest` `python3` `python` `perl` `cargo` `sleep` `paste` `ps` `lsof` `rev` `base64` `sips` `hostname`

이 목록은 "안전한 프로그램"이 아니라 "나올 만한 프로그램"이다. `pnpm install`처럼 하위 명령이 외부인 것은 지금 판정이 그대로 묻는다. 목록에 없는 프로그램은 처음 한 번 묻고, 「늘」을 고르면 3번으로 아는 프로그램이 된다.

### 5.4 묻는 모양

- **모르는 프로그램:** 지금의 실행 묻기를 그대로 쓴다(열쇠 `run:<프로그램>`, 이름 「실행 · 프로그램」, 「늘」 있음).
- **그 밖:** 한 번 묻기. 이름은 「읽지 못한 명령 · 까닭」이고 「늘」은 없다(열쇠 `unread:<명령>`, 하는 일은 실행). 까닭은 짧은 말 하나다: 변수로 정한 프로그램 · 모르는 문법 `이름` · 풀지 못한 치환 · 값을 모르는 변수.

묻기 카드는 지금 부품을 그대로 쓰고 글만 더한다(한국어 · 영어).

중앙 대화 아래의 하위 대화에서는 크리티컬하지 않은 묻기에 중앙이 답한다(`agentKid.ts`의 `criticalOf`: 삭제 · 외부 · 비밀 · 노트 고치기만 사용자에게 간다). 새 묻기는 하는 일이 실행이라 지금의 실행 묻기처럼 중앙이 답한다. 사용자에게 보낼지는 10절에서 정한다.

## 6. 생각한 방법들

- **가. 셸만 닫기 (고름).** 위 설계. 새로 묻는 줄 1% 안팎, PR 하나. 인라인 코드로 지우는 길은 그대로 열려 있다.
- **나. 가 + 인라인 코드도 묻기.** 대화마다 열한 번쯤 더 묻는다. 스크립트 파일을 쓰고 돌리면 지나가므로 닫히지 않는다. 묻는 값만 치르고 얻는 것이 없어 버렸다.
- **다. 가 + OS 격리.** 판정이 무엇을 놓치든 작업 폴더 밖을 못 쓰게 한다. 방향은 옳지만 값이 불확실해 시험부터 했다(8절). 가와 겹치지 않으므로 가를 먼저 하고 따로 설계한다.

사용자가 2026-11-26에 "가 + 격리 시험"을 골랐다.

## 7. 끝나는 조건

PR이 다음을 모두 보이면 끝난 것이다.

1. **불변식.** 무작위로 만든 줄에서, 프로그램 자리(치환 · 감싸 돌리기 안 포함) 어디든 목록 밖 이름이 있거나 5.2의 나 · 다 묶음 조각이 하나라도 들면 읽지 못한 것으로 나온다. 읽은 것으로 치는 조각만으로 만든 줄은 읽은 것으로 나온다(생성 테스트).

## 8. 격리 시험 결과 (2026-11-26, 버린 시험)

저장소 밖에 복사본과 작업 폴더(git worktree)를 만들고, 앱이 에이전트를 띄우는 옵션에 에이전트 라이브러리의 `sandbox` 옵션만 더해 정해 둔 명령을 돌렸다. 맥에서만 했고 시험 폴더는 지웠다.

| 본 것 | 결과 |
| --- | --- |
| 앱의 판정이 명령을 계속 보는가 | 본다. 격리를 켜도 명령마다 앱에 묻는다(`autoAllowBashIfSandboxed: false`) |
| 작업 폴더 밖 쓰기 (셸 · 파이썬 코드, 홈 · 옆 폴더 · 파일 지우기) | 모두 막힘 |
| 작업 폴더에서 커밋 (저장소 본체의 `.git`에 씀) | 설정 없이 됨. `.git/hooks`에 쓰기는 막힘 |
| 임시 폴더 쓰기 | 됨 |
| 모르는 호스트로 나가기 | 호스트마다 앱에 묻는다(`SandboxNetworkAccess`). 앱이 호스트를 판정할 수 있다 |
| 로컬 포트 열기 | 기본은 막힘, `allowLocalBinding`으로 됨 |
| `gh` | 기본은 인증서 확인 실패, `enableWeakerNetworkIsolation`으로 됨(이 설정은 격리를 약하게 한다) |
| `pnpm` | 그대로는 모든 명령이 저장소 잠금에서 실패. 버전 바꿔 쓰기를 끄면(`manage-package-manager-versions=false`) 테스트 · 타입 검사가 됨 |
| 화면 그림 (`pnpm shots`) | 안 됨. 서버가 쓰는 유닉스 소켓이 막히고, 그것을 열면 파일 감시가 파일 한도를 넘는다. 풀지 못했다 |
| 폴더 밖 읽기 | 열려 있다(홈의 폴더 목록이 읽힌다). 읽기를 막으려면 따로 설정해야 한다 |

**읽을 수 있는 것.** 맥에서는 격리가 벽이 될 수 있다: 인라인 코드로도 폴더 밖을 쓰지 못했고 앱의 판정과 함께 돈다. 넣으려면 풀 것이 셋이다: 화면 그림용 서버, `pnpm` 설정, `gh`를 약한 격리로 돌릴지 앱이 대신 할지.

**보지 않은 것.** 리눅스(클라우드)와 윈도우, 실제 앱 고치기 대화 전체 흐름(앱 도구 · 올리기), 연구 프로젝트 대화(TeX 컴파일 · 파이썬 환경), 브라우저 띄우기, 처음 꾸러미 깔기.

격리를 넣을지는 이 문서의 범위가 아니다. 위 셋을 푸는 시험을 한 번 더 한 뒤 따로 설계한다.
