# 피드백 규약

앱 사용자가 화면에 남긴 피드백을 코딩 에이전트가 처리하고, 사용자가 그 처리에 다시 답하는 흐름의 규약이다. 특정 앱에 묶이지 않게 썼다. 연구 작업대가 첫 구현이고, 퀀텀캐드와 Telos 공부 앱도 같은 규약을 따른다. 새 앱에 넣는 순서는 [new-app.md](new-app.md), 에이전트가 처리할 때 지키는 규칙은 [agent.md](agent.md), 차례 계산의 공통 시험 사례는 [cases.json](cases.json)이다.

규약은 칸 이름과 뜻, 차례 규칙만 정한다. 담는 모양(YAML · JSON · 항목마다 파일)과 화면 모양은 앱이 정한다.

## 1. 세 사람과 세 파일

쓰는 사람마다 파일을 나눈다. 한 파일을 둘이 쓰지 않으므로 맥 · 폰 · 에이전트가 동시에 써도 부딪히지 않는다.

| 모듈 | 파일 (작업대) | 쓰는 쪽 | 내용 |
| --- | --- | --- | --- |
| 원문 | `feedback/YYYY-MM-DD.md` | 앱 (사용자가 남김) | 피드백 원문. 에이전트는 고치지 않는다 |
| 처리 기록 | `feedback/status.yaml` | 에이전트만 | 상태, 이해한 요구, 원인, 처리, 다시 처리한 이력, 코멘트에 단 답 |
| 사용자 답 | `feedback/reviews.yaml` | 앱만 | 승인 · 반려 · 진행 · 중단, 그 이력, 코멘트 |

세 파일은 같은 **키**로 이어진다: `<날짜> <HH:MM> <부위>`(예: `2026-10-04 09:30 홈 › 할 일`). 같은 날 같은 분 · 같은 부위가 또 있으면 뒤의 것부터 ` #2`, ` #3`을 붙인다. 원문의 유형이나 글을 고쳐도 키는 그대로다.

시각은 앱이 도는 컴퓨터의 시간대로, 시간대 표기 없이 `YYYY-MM-DDTHH:MM`으로 쓴다. 차례 계산은 시각을 글자로 비교하므로 한 앱 안에서 시간대를 섞지 않는다.

## 2. 모듈 지도

기능을 아홉 모듈로 나눈다. 앞의 여섯이 최소 묶음이고, 뒤의 셋은 피드백이 쌓이면 더한다. 모듈 사이에 오가는 것은 위의 세 파일과 차례 계산의 결과뿐이다.

| 모듈 | 하는 일 | 읽는 것 → 쓰는 것 | 작업대 구현 |
| --- | --- | --- | --- |
| M1 남기기 | 피드백 모드에서 부위를 고르고 유형 · 글을 받는다 | 화면 → 원문 | `apps/web/src/FeedbackMode.tsx`, `feedbackDraft.ts` |
| M2 원문 | 원문 항목을 덧붙이고, 고치고, 지우고, 키를 만든다 | 원문 | `apps/server/src/feedback.ts` 앞부분 |
| M3 처리 기록 | 에이전트의 기록을 읽는다 (쓰기는 에이전트가 파일에 직접) | 처리 기록 | 같은 파일 `readFeedbackStatus` |
| M4 사용자 답 | 답 단추 · 코멘트 · 내 글 고치기 · 되돌리기를 적는다 | 사용자 답 | 같은 파일 `setFeedbackReview` 등 |
| M5 차례 | 항목마다 누구 차례인지 정한다. 순수 함수 | 셋 → 차례 | `packages/core/src/feedback-buckets.ts` |
| M6 모아 보기 | 차례로 거른 표, 제자리 펼침(요약 · 대화 · 입력), 레일 수 | 셋 + 차례 → 화면 | `apps/web/src/FeedbackPage.tsx`, `feedbackThread.ts` |
| M7 에이전트 도구 | 에이전트 차례 목록과 그 까닭, 최근 교훈. 읽기 전용 | 셋 + 차례 → 글 | `scripts/agent-feedback.mjs`, `packages/core/src/feedback-lessons.ts` |
| M8 올리기 | 원문 · 사용자 답을 저장소에 올린다 | 원문 · 답 → git | `apps/server/src/feedback.ts` 끝부분 |
| M9 마무리 | 같은 지적 합치기, 반영 버전, 전후 그림, 그 자리로 가기, 승인된 것 정리 | 처리 기록 | `feedbackJump.ts`, 서버 `listAllFeedback` |

자료 모양의 정본은 `packages/core/src/contract/feedback.ts`(zod)다. 다른 언어의 앱은 그 칸 이름을 그대로 쓴다.

## 3. 원문 항목

| 칸 | 뜻 | 필수 |
| --- | --- | --- |
| date · time | 남긴 날짜와 분 | 예 |
| kind | 사용자가 고른 유형: `수정` · `질문` · `제안`. 고르지 않으면 등록하지 않는다 | 예 |
| target | 화면 부위 이름, 바깥부터 ` › `로 잇는다 (`사이드바 › 목차`). 부위 없이 남기면 `(부위 없음)` | 예 |
| text | 사용자의 글 | 예 |
| route | 화면 주소 | |
| snippet | 가리킨 부위의 글자, 또는 사용자가 고른 글 | |
| viewport · theme | 창 크기와 라이트 · 다크 | |
| version | 남길 때 돌던 앱 버전(커밋) | |
| picture | 남긴 순간의 화면 그림 경로 | |

부위 이름은 피드백 기록의 주소라서 바꾸지 않는다(작업대는 `data-ui`). 옛 기록에는 `디자인` · `버그` · `기능` · `미분류` 유형도 있다.

## 4. 처리 기록 (에이전트만 쓴다)

| 칸 | 뜻 |
| --- | --- |
| state | 유형별 답: 수정 → `반영` · `거절` · `확인 필요`, 질문 → `답변`, 제안 → `동의` · `나중에` · `거절`. 옛 기록은 `보류` · `승인` |
| ask | 사용자에게 묻는 것 한 문장. 붙으면 결정을 묻는 답이 된다 |
| clean · understood · cause · note | 문법을 고친 원문, 읽어 낸 요구, 원인, 처리(답). note 첫 줄은 [agent.md](agent.md) 3의 정한 말 |
| commit · version · pictures | 고친 곳, 그 고침이 들어간 앱 버전, 전후 그림 `[전, 후]` |
| handled_at · by | 처리한 시각과 에이전트(`claude` · `codex`) |
| rework | 다시 처리한 사용자 답의 시각(그 답의 `at`과 같은 글자) |
| revised[] | 다시 처리하기 전의 처리: `at`(돌려보낸 답의 시각), understood · cause · note · commit · handled_at · by, 그리고 `miss`(까닭) · `lesson`(한 줄 교훈) |
| replies[] | 코멘트에 단 답: `{ at, to: 그 코멘트의 at, note, by }` |
| merged_into | 같은 지적이라 합친 대표 항목의 키 |
| theme · area · kind | 에이전트가 묶은 갈래, 화면 영역, 다시 가린 종류 |

`miss`는 `답 불분명` · `덜 고침` · `잘못 읽음`(에이전트의 실수) · `새 요구` · `논의`(실수 아님) 가운데 하나다.

## 5. 사용자 답 (앱만 쓴다)

| 칸 | 뜻 |
| --- | --- |
| verdict · at · note | 최신 답과 시각, 덧붙인 말. verdict는 `승인` · `반려` · `진행` · `중단` |
| history[] | 그 전의 답, 오래된 것부터 |
| comments[] | 처리를 바꾸지 않는 물음 · 덧붙임 `{ at, note }` |
| edited | 사용자가 그 글을 고친 시각 (답 · 코멘트 모두) |

답 단추는 처리 기록에 따라 두 묶음이다.

- **결과를 알린 답**(`반영` · `답변` · `거절` · `나중에`): 질문 · 수정 · 승인. 수정은 `반려`로 저장한다.
- **결정을 묻는 답**(`확인 필요` · `동의` · `ask`가 붙은 `답변` · `보류`): 질문 · 중단 · 진행. 승인은 없다.

질문은 `comments`에 더하고 verdict는 그대로 둔다. 입력란이 비면 승인만 켜고, 글을 써야 질문 · 수정이 켜진다. 마지막 답은 되돌릴 수 있다(verdict를 지우고 history는 남긴다). 앱은 결정을 묻는 답에 승인을, 반려에 빈 이유를 받지 않는다.

## 6. 차례

항목마다 다음 일을 할 사람이 정해진다. 위에서부터 처음 맞는 줄이 답이다.

1. 답 없는 코멘트가 있으면 **대기**(에이전트 차례). 코멘트에 단 답(`replies`의 `to`)이 없거나, 답한 뒤에 코멘트를 고쳤으면 답 없는 것이다.
2. 결정을 묻는 답이고 사용자가 아직 진행 · 중단하지 않았으면 **확인 필요**(사용자 차례, 답할 것). 날짜와 상관없다.
3. 결과를 알린 답이고, 사용자 답이 아직 없으며 남긴 지 7일이 안 됐거나, 반려 · 진행을 다시 처리한 뒤면 **확인 필요**(확인할 것).
4. 처리 기록이 없거나, 최신 답이 반려 · 진행인데 아직 다시 처리하지 않았거나(`rework` ≠ 그 답의 `at`), 다시 처리한 뒤에 사용자가 그 글을 고쳤거나(`edited` > `handled_at`), 물음 없는 보류면 **대기**.
5. 나머지는 **완료**. 승인 · 중단한 것, 7일 동안 답이 없던 결과가 여기 든다.

에이전트 차례의 까닭은 이름을 정해 둔다: `comment` · `rework` · `proceed` · `edited` · `new` · `hold`. 레일(왼쪽 띠)의 수는 사용자 차례인 항목 수다. 화면 · 레일 · 에이전트 도구는 같은 차례 함수를 써서 서로 어긋나지 않게 한다.

차례를 구현한 앱은 [cases.json](cases.json)을 그대로 돌린다. 사례 하나는 항목(`item`)과 기대하는 `bucket` · `user`(`answer` · `confirm`) · `agent`(까닭 목록)다. 규칙을 바꾸면 이 파일을 먼저 고치고, 모든 앱의 시험이 그것을 따라간다.

## 7. 앱마다 다른 것

| | 연구 작업대 | 퀀텀캐드 | Telos 공부 앱 |
| --- | --- | --- | --- |
| 담는 모양 | 날짜 md + YAML 둘 | 날짜 md + JSON 둘 | 메모마다 JSON: 원문 `sync/notes/`, 처리 기록 `sync/replies/` · `requests/all.json`, 사용자 답 `sync/reviews/` |
| 차례 구현 | TypeScript (core) | Python (`feedback.py`) | JavaScript (앱 부품 `50-feedback-turn.js`, 폰 · 맥 · 에이전트 명령이 함께 씀) |
| 공통 시험 사례 | `feedback-cases.test.ts` | `tests/test_feedback_cases.py` | `tools/check_feedback.mjs` |
| 에이전트 도구 | `pnpm agent:feedback` | `python -m qcad_gravity_api.feedback` | `node tools/feedback_turn.mjs` |
| 기록 위치 | 관리자 개인 저장소 `feedback/` | 프로젝트 저장소 | 앱 저장소 `sync/` |
| 앱만의 것 | | 에이전트 차례인 항목에는 답을 받지 않음 | 고른 글 인용, 질의 즉답, 질의 · 메모는 승인 단계 없음 |
