# Agent entry point (MCP)

[한국어](agent-mcp.ko.md)

Agents such as Claude Code and Codex read Emergence Workbench projects, notes, records, delegated tasks and concept notes **through the app server**. The MCP tools do not open files directly: they use the same API as the screen, so they see the same content and the same hashes. The write tools are `edit_note` and `edit_concept`, which change notes, `answer_record` (10/15), which answers a question or instruction record, `add_record` (10/15), which leaves a question or memo for the user under the agent's name, the flow tools (10/20), and `add_task`, `report_task` and `add_journal` (10/21), which create a task, write a task's proposal or result, and add a line to today's journal. Agents use these instead of reading `workbench/STATUS.md` or editing workbench files: the outputs are short and the work shows up in the app (10/21: agents in the research repositories were reading the 40KB STATUS.md and editing task and journal files by hand). The edit tools work like this: the agent writes at once, the app keeps the text before the edit as a baseline, and the user approves, reverts or edits each changed paragraph on the edit review screen (a project's "Edit review" section `#/r/<project>/edits` for research notes, `#/review` for concept notes). Notes the user has reviewed need the user's permission in the conversation first. Each edit records which agent made it, from the name the client sends when it connects (`clientInfo.name`: Claude Code → `claude-code`, Codex → `codex`, others as sent). The name is what the client says about itself and is not checked. Files an agent changes directly, without the app, leave no such record; for those, see the commit author. In the review the user can ask about a changed paragraph: the question is saved as a note record with `edit: 질문` or `edit: 수정` (`docs/repo-format.md` §6.2). The app asks Claude on the Mac right away; when that is not available the record stays unanswered and shows up in the agent's queue. For `수정`, revise the paragraph with `edit_note`, then answer the record with `answer_record`.

## Before you start

- The app server must be running on the Mac (the installed service, default `http://127.0.0.1:5174`). If it is off, every tool answers "Cannot reach the Emergence Workbench app server" and does nothing.
- To use a server at another address, set `RW_URL`. For sample mode (`pnpm dev`): `RW_URL=http://127.0.0.1:8130`.

## Register it

The Mac installer (`zsh scripts/install.sh`, [mac-setup.md](mac-setup.md)) registers both of these for you. To do only this step, run `pnpm agents:register` (`scripts/register-agents.sh`: skips what is registered, re-registers when the app folder moved). By hand, put the path of the app folder in `<app folder>`. Nothing is added to your research repositories (user-scope registration).

**Claude Code**

```sh
claude mcp add --scope user emergence-workbench -- node <app folder>/scripts/mcp.mjs
```

Settings › Accounts › Agent connection shows this line with the real app folder (copy button) and when an agent last called the app: the MCP tools send an `x-rw-agent` header with the agent name, and the app keeps the last call in `agent-seen.json` in the settings folder.

**Codex** (`~/.codex/config.toml`)

```toml
[mcp_servers.emergence-workbench]
command = "node"
args = ["<app folder>/scripts/mcp.mjs"]
```

Inside the app folder, `pnpm mcp` also starts it (it speaks MCP over stdio, so you never type into it).

## Tools (read-only except edit_note, edit_concept, answer_record, add_record, flow_add, flow_update, flow_review, add_task, report_task and add_journal)

When it connects, the server tells the agent which tools to use in which order for each kind of job (`INSTRUCTIONS` in `apps/server/src/mcp.ts`): start with `rules`, then `overview`, then `project_status`. If you add or rename a tool, update that order too; `mcp.test.ts` checks that every tool name there exists.

| Tool | What it does | API it calls |
| --- | --- | --- |
| `rules` | What to read before starting: safety rules, the common research rules (one file for every research repository, when the personal repository copy has `rules/research.md`) and, with `project`, that repository's `AGENTS.md` and `CLAUDE.md`. Longer rules that only some work needs are listed by name and size, and `part` returns one: `tasks` (delegated-task rules, `docs/agent-delegated-work.md`) or `concepts` (the concept-note section of the shared library README). Read this first | `GET /api/rules/common`, (the document in the app folder), `GET /api/concepts/rules`, `GET …/:rid/agent-rules` |
| `list_projects` | Registered projects: id, title, repository path, progress | `GET /api/researches` |
| `overview` | Every active project in one table: the user's turn (notes to review, delegated-task results to judge, agent edits; the same count as Home's "needs review"), the agent's turn (unanswered questions, working tasks, open to-dos), repository sync, last record. Use it to choose where to work | `GET /api/agent-overview` |
| `project_status` | Short project summary: the header, the goal and the sections that say what to do now (to-dos, delegated tasks, the flow summary, pending questions and instructions, reviews), with every other section listed by name and size. `section` returns one section of `workbench/STATUS.md`, `full` the whole file | `GET …/:rid/agent-status?view=summary`, `?section=<name>` |
| `list_notes` | Notes: body file, record name `target` (Markdown notes and block notes; absent for `main.tex`), state, condition to reopen, topic (filter with `status`) | `GET …/:rid/notes` |
| `list_edit_reviews` | Pending agent edits and permission requests; optional `project` limits the list to one project, otherwise all projects and concept notes | `GET /api/agent-edits?scope=` |
| `read_note` | A note's body and hash | `GET …/:rid/manuscript/part`, block notes `GET …/:rid/blocks/:id` |
| `read_records` | Records on a note or project (memos, to-dos, questions and answers, highlights) and hash. Targets are `project`, `note-<folder>`, `topic-<id>`, `flow-<id>` and so on; `part` · `partText` are the screen part the user pointed at | `GET …/:rid/comments/:target` |
| `list_records` | Every record of a project in one list (project, notes, topics, flow dots; highlights excluded), filtered by kind, state or target (exact, or a prefix such as `topic-`). `unanswered: true` gives only the user's questions and instructions (지시, 10/15: an agent does it, then answers) waiting for an answer. `replied: true` gives questions an agent asked that the user has answered: act on the answer, then `answer_record` closes it (끝냄). `unsorted: true` gives records left as 자동 and not yet sorted. `by` is the agent that wrote a record (absent = the user); answers by `사용자` are the user's follow-ups. Rows are short (body and last answer cut at 300 characters, answer count); `full: true` gives everything. Without the app server, `pnpm agent:records <repo>` lists the same rows and `pnpm agent:answer <repo> <target> <id> "<answer>"` writes the same answer. Concept-note records in the knowledge library use `project: _library` (targets `concept-<id>`; `docs/repo-format.md` §10.5), and the two commands also take the library folder | `GET …/:rid/records` |
| `list_tasks` · `read_task` | Delegated tasks, and every field of one | `GET …/:rid/tasks`, `…/tasks/:id` |
| `add_task` | Create a task file `{ title, task, endCondition?, topic?, agent?, references?, avoid? }` for a to-do, handoff or proposal of new work, instead of writing `workbench/tasks/*.md` | `POST …/:rid/tasks` |
| `report_task` | Write the report of a task in progress (`working`) with the hash from `read_task`. `kind: proposal` with `endCondition` (and `reason`) → `proposed`. `kind: result` with `conclusion`, `endCheck`, `summary`, `evidence` and optionally `ask`, `issues`, `next`, `outputs`, `checkMachine` → `result`. The app writes the YAML front matter (so commas and colons cannot break it) and the two body sections; text already in a section is kept and the new text goes under a dated `###` heading. Never `done` | `POST …/:rid/tasks/:id/report` |
| `add_journal` | Append a memo line to today's journal `{ text, target? }` (what you did and the files you touched), instead of writing `workbench/log/<date>.md` | `POST …/:rid/journal` |
| `search_library` | Find concept notes and papers (name, alias, author, year, arXiv id). Concept notes are also found by their text, with `hits` for each matching line (body line number, the heading it falls under, the line), so you can read just that section | `GET /api/search/catalog`, `GET /api/concepts/search` |
| `read_concept` | A concept note's front matter, body, hash and check state (ok, changed, none) | `GET /api/concepts/:id` |
| `edit_note` | Change a project note (not a manuscript) by exact text replacement `{ old, new, reason }` with the hash from `read_note`. `reason` is required: one line on why, shown under the changed paragraph. The optional `summary` is one line on why the whole batch was made, shown above the review as "Why the agent made these edits": write it in the user's language without session-internal numbering, and leave it out when the reasons already say it (10/21). Written at once and shown to the user for review paragraph by paragraph. A note with status solved is refused on the first try (428) and the user is notified; ask in the conversation, then send again with `approved: true` | `POST /api/agent-edits/write` |
| `edit_concept` | The same for a concept note's body (front matter stays). A note with `checked: ok` needs permission the same way; locked notes are never changed | `POST /api/agent-edits/write` |
| `flow_search` | Earlier dots of the project flow matching the words (title, fields, run parameters, reasons), best first, one short row each: state, parameters, result, and why a dot was refuted or dropped. Use it before starting a calculation or proof | `GET …/:rid/flow/search?q=` |
| `flow_read` | One flow dot with every field, its evidence and step checks, and the gaps the app found | `GET …/:rid/flow/:id` |
| `flow_add` | Add a dot when a piece of work starts (usually `active`, with its criterion). The app records the start date and your agent name (`by`); pass `task` with the delegated task id when the work belongs to one. Extra fields go through the same finishing gate as `flow_update` | `POST …/:rid/flow` then `PATCH …/:rid/flow/:id` with `gate: true` |
| `flow_update` | Change a dot. Finishing (`done`) or pausing is refused while required fields are empty (`docs/repo-format.md` §14 "해결 문턱"); the error names them. Question wording, origin links and dropping a branch are refused (the user decides them) | `PATCH …/:rid/flow/:id` with `gate: true` |
| `flow_review` | Agent review of one piece of evidence (`ev`) or one proof step (`step`), as `role: agent`, with a hash of what was checked | `POST …/:rid/flow/:id/review` |
| `answer_record` | Write an answer under a question or instruction record `{ target, id, answer }`. For an instruction, do the work first (notes with `edit_note`). The answer header carries your agent name and the record becomes 답함 (answered). Appending, so no hash | `POST …/:rid/comments/:target/:id/answers` |
| `add_record` | Leave a record for the user `{ file or target, kind: 질문 \| 메모, text, quote?, line? }`, written with `by` = your agent name. A 질문 asks the user to check or decide something (for example a passage of a note you wrote, anchored by `quote`): it is the user's turn (orange in the app, counted in Home's "needs review") until the user answers in the app, which appends `### 답 · 사용자` and sets 답함. Read the answer with `read_records`. Appending, so no hash | `POST …/:rid/comments/:target` |
| `app_submit` | Only inside an app conversation (the in-app agent that fixes the app itself, 10/21). Commits every change in that conversation's work folder (a separate git worktree), pushes its `claude/app-…` branch and opens the pull request `{ title, body }`, or adds to it. Other open pull requests do not block it (each conversation has its own branch). The agent runs checks in its work folder itself (type check · tests · screen pictures) but never pushes, opens or merges PRs or touches the app service; GitHub CI runs the checks again | `POST /api/agent-chats/:id/app/submit` |
| `app_checks` | Only inside an app conversation. That pull request's CI: each check's state, `done`, `ok`, and the end of the failed log; `wait` (minutes, up to 10) waits until the checks finish | `GET /api/agent-chats/:id/app/checks` |
| `feedback_answer` | Only inside an app conversation that handles a feedback item (handed off from the feedback screen). The app writes the handling record (`status.yaml`): state and answer, or replies to comments; when redoing a revision request it moves the previous handling to `revised`. `after` = screen picture name from this PR's CI, saved with the feedback's own picture as 전/후 | `POST /api/agent-chats/:id/feedback/answer` |

## Rules it keeps

- To change a note or concept note, prefer `edit_note` / `edit_concept`. For other writes, call the app server API (`GET /api` gives the main routes and how to use them, `GET /api?all=1` every route) and send the hash you read as `baseHash`. If the file changed in the meantime, the write is refused with 409. Creating, appending and one-field changes take no hash, and journal edits send the entry's current text as `was`; `GET /api` and `docs/repo-format.md` §12 list them.
- You may also edit repository files directly, including when the app server is stopped: tell the user when it cannot be reached, follow `docs/repo-format.md`, and run `pnpm --dir <app folder> agent:check <repository>` afterwards. Notes and concept notes the user has reviewed still need permission in the conversation; manuscripts are edited only when the user asks. Locked concept notes are never changed.
- Instructions (지시): Settings › Agents chooses whether Claude on the Mac carries them out itself, right away or once a day at a chosen time (default: no, an agent session picks them up). It runs one at a time with read-only tools and answers as `claude`, with note changes as fix blocks the user applies. Records it already answered are no longer in `unanswered`.
- Check pending edits with `list_edit_reviews` or the project summary. Do not reintroduce paragraphs the user reverted. Reverting an agent edit to a project note or block note appends a status record to that project’s journal; concept notes have no project journal, so their reverts are not recorded there.
- Each research repository's own `AGENTS.md` and `CLAUDE.md` come before this entry point.
- Code: `apps/server/src/mcp.ts` (tools), `scripts/mcp.mjs` (stdio start), tests `apps/server/src/mcp.test.ts`.

## Conversations the app starts (agent chats, 10/21)

The app can also start Claude Code on the Mac itself (Claude Agent SDK, `apps/server/src/agentChats.ts` · `agentRunner.ts`, API `/api/agent-chats`). Each conversation belongs to one project and has a scope (the project, one topic or one note) and a write level (read only, or notes and records). The same MCP tools are attached in-process, and the app decides every tool call:

- Reading the project, the shared library and other registered projects is allowed; reading outside the scope shows as "outside the scope" in the conversation. Reading other folders asks the user.
- Files cannot be written directly (`Write`, `Edit` …). Notes change only through `edit_note`, so they land in edit review. Changes outside the scope, to another project or to concept notes are refused, and the agent is told to say what should change instead.
- While a conversation changes a note it holds that file; another conversation cannot change it until the turn ends. `GET /api/agent-work` lists running conversations and the files they hold.
- Commands, web access and unknown tools ask the user (an approval card); "always" covers only the same command in that conversation, and the always-list can be cleared one by one (`POST /api/agent-chats/<id>/forget`).
- How much to hand over is one setting per conversation (`mode`, with `write`): read only · ask first (every note edit asks too) · plan first (SDK plan mode; note edits are refused until the user approves the plan card for `ExitPlanMode`) · edit right away. Model and thinking (`low` · `medium` · `high` · `xhigh` · `max`, only those the model takes) can change mid-conversation (`POST /api/agent-chats/<id>/settings`) and apply from the next turn. The models offered come from the Mac's Claude Code, with versions (`GET /api/agent-chats/models`: the aliases `default` · `opus` · `sonnet` · `haiku` and ids such as `claude-opus-5`, the real model `resolved`, the thinking levels it takes; asked without a prompt and kept for 30 minutes, empty when Claude Code cannot start). `default` is that account's Claude Code default (user settings are not read).
- A message can carry attachments (`attach`: note, topic, file, selection, paper, record; the agent reads those first) and up to four images. A message sent while the turn runs waits and starts the next turn. `TodoWrite` shows as one to-do card per turn, and every allowed `edit_note` as an edit card (+/−, link to edit review); the conversation keeps `todos` and the changed files.
- At most two conversations run at once; the rest wait in a queue. Repository and user settings of Claude Code (hooks, allow rules) are not loaded. Conversations are stored in the app's config folder (`agent-chats/<id>.json`), not in the research repository.
